# 刷机与使用说明

面向 Hi3518EV300 + F23 + 16MB SPI NOR 的 OpenIPC 固件。

本文默认讲**产物一**（`hi3518ev300_fpv_wfbng`，wfb-ng 空中端）。
**产物二**（`hi3518ev300_apfpv`，纯 AP 推流）刷机流程完全一样，
只是文件名换成 `openipc.hi3518ev300-nor-apfpv-split.tgz`，
装好之后没有 `wifibroadcast` 命令、改用 `apfpv`
—— 那份的取流、配置与排障见 [`AP推流说明.md`](AP推流说明.md)。

---

## 1. 拿到镜像

CI 跑完，artifact（`openipc-<defconfig>-<sha>`）里就这几样
（下面以 FPV 那份为例，AP 那份把 `fpv` 换成 `apfpv`）：

| 文件 | 大小量级 | 用途 |
|---|---|---|
| `openipc.hi3518ev300-nor-fpv-split.tgz` | ~12 MB | **首选**。里面有 `firmware.bin.hi3518ev300` 和它的 `.md5sum`。`sysupgrade` 直接吃这个包 |
| `firmware.bin` | 同上 | 裸镜像，U-Boot TFTP / 编程器用。内容和 tgz 里那份一样 |
| `SHA256SUMS` | 几百字节 | 先核对这个 |

`firmware.bin` 是 NOR split 布局：**uImage 在前，squashfs 紧接在下一个
64 KiB 边界**，整块写到 flash 的 `0x50000`，内核启动时自己切开。

### 1.1 先校验

```bash
sha256sum -c SHA256SUMS
```

### 1.2 从 tgz 里取出镜像并核对 md5

```bash
tar -xzf openipc.hi3518ev300-nor-fpv-split.tgz
# 得到 firmware.bin.hi3518ev300 与 firmware.bin.hi3518ev300.md5sum
md5sum -c firmware.bin.hi3518ev300.md5sum
mv firmware.bin.hi3518ev300 firmware.bin      # 后面命令按这个名写
```

两层校验不是多余的：`SHA256SUMS` 证明从 CI 下载没坏，`.md5sum`
证明包内镜像与构建时一致。

## 2. 刷机

### 2.1 前置：备份原厂固件

**在做任何事之前**把整片 16 MiB 读出来存好。变砖之后这是唯一能回头的路。

**注意 `/dev/mtd0` 不是整片。** 它是第一个分区（split 布局下通常是
`boot`，只有 320 KiB）。直接 `dd if=/dev/mtd0` 得到的备份救不了砖。
要按分区逐个读再拼起来 —— 先看清楚布局：

```bash
cat /proc/mtd        # 每个分区的名字、大小、擦除块大小
```

然后把每个分区按 `mtd0 mtd1 mtd2 …` 的**地址顺序**读出来拼接（NOR 的
分区在物理上是连续的）：

```bash
mkdir -p /tmp/bk && cd /tmp/bk
for i in $(cut -d: -f1 /proc/mtd | tr -d 'mtd'); do
    dd if=/dev/mtd$i of=mtd$i.bin 2>/dev/null
done
cat $(ls mtd*.bin | sort -V) > /tmp/backup_full.bin
ls -l /tmp/backup_full.bin        # 必须正好 16777216 字节
```

最后一行是关键：**大小必须等于 16777216（16 MiB）**。小于这个数说明分区
之间有空洞，或者漏了分区 —— 这种备份不要依赖。

> 最稳妥的还是 §2.3 的编程器直读：它不依赖设备能启动，也不受分区表影响。
> 设备已经变砖、或者原厂固件本身有问题时，只有这一条路。

### 2.2 方式 A：U-Boot + TFTP（推荐）

串口进 U-Boot（Hi3518EV300 常见 115200 8N1）：

```
setenv ipaddr 192.168.1.10
setenv serverip 192.168.1.2
tftp 0x42000000 firmware.bin
sf probe 0
sf erase 0x50000 ${filesize}
sf write 0x42000000 0x50000 ${filesize}
reset
```

**三个必须注意的点：**

1. **用 `${filesize}`，不要写死长度。** `tftp` 成功后 U-Boot 会把传输字节数
   放进 `${filesize}`。写死一个分区全长（比如 `0xFB0000`）会把文件末尾之后
   RAM 里的内容也一起烧进 flash —— 那段虽在本分区内，但会把尾部为 overlay
   保留的 256 KiB 覆盖掉。

2. **一定要 `sf probe 0` 并确认它打印出了正确的 flash 容量**（16 MiB）。
   probe 失败时后面的 erase/write 会静默无效。

3. **`sf erase` 会把整个固件分区擦掉**，包括 `rootfs_data`（你之前改过的
   配置）。要保留就别擦，改 `sf write` 只覆盖镜像占的长度；但布局变化时
   必须擦，否则新旧内容会混在一起。

> 开始写之前先 `sf read 0x42000000 0x50000 0x100` 看一下现有头 256 字节，
> 确认这块确实是固件分区而不是别的。写错了要拆 flash 才能救。

> 若这块板的 bootloader 只读固定 2 MiB（`BR2_OPENIPC_NOR_KERNEL_READ_SIZE`
> 默认就是 `0x200000`），那它读不到 split 布局的后半段。构建时
> `CHECK_KERNEL_READ` 已经强制 uImage ≤ 2 MiB，所以正常情况没问题；
> 但如果你是拿别人的 bootloader 换过来的，先确认它读多少。

### 2.3 方式 B：microsnander（SPI 编程器）

拆下 flash 或飞线接编程器。**不要照抄参数** —— 芯片型号选择因版本而变，
先列出来再选：

```bash
microsnander -l                    # 列出支持的芯片
microsnander -c <上面列出的编号> -w firmware.bin
```

写之前先**把原片整片读出来备份**（见 §2.1），这一步只能做一次机会。

> 具体参数以 `microsnander -h` 的输出为准。本工程没在真实 flash 上跑过这个
> 工具，所以这里只给形式，不给你不能验证的具体数字。

### 2.4 方式 C：sysupgrade（已在跑 OpenIPC 时）

**首选直接喂 tgz**，它会校验 SoC、结构和包内 md5：

```bash
scp openipc.hi3518ev300-nor-fpv-split.tgz root@192.168.1.10:/tmp/
ssh root@192.168.1.10 'sysupgrade -n /tmp/openipc.hi3518ev300-nor-fpv-split.tgz'
```

`-n` 表示不保留旧配置。

也可以直接给裸镜像，上游脚本同样接受（会校验 uImage + squashfs 结构）：

```bash
scp firmware.bin root@192.168.1.10:/tmp/
ssh root@192.168.1.10 'sysupgrade -n /tmp/firmware.bin'
```

两种方式在 split 布局下都不能只更新内核或只更新 rootfs —— 上游会直接拒绝并
提示用 `-split.tgz`，因为 split 布局的 kernel 与 rootfs 是同一个文件。

## 3. 首次启动

接串口看日志。正常会看到：

```
Detected driver: <驱动名>
wfb_dev=wlan0
channel=161 width=HT20 mcs=1 fec=8/12 power=...
video: 1920x1080@30 h264 10000kbps cbr
Starting wfb_tx
Starting wfb_tun
Starting msposd
```

日志用 `logger` 打的，所以也能：

```bash
logread -f | grep wifibroadcast
```

### 3.1 确认网卡被识别

```bash
wifibroadcast detect
```

输出形如 `0bda:8812 -> 8812au`。若显示 `未知`，查 `/etc/fpv-usb-ids.txt`。

**如果输出是空的（一条 USB 设备都没有）**，那多半不是驱动问题，而是 USB 主机口没起来：

本平台内核用的是 `CONFIG_USB_DWC3=y` + `CONFIG_USB_DWC3_DUAL_ROLE=y`
（见 `br-ext-chip-hisilicon/board/hi3516ev200/hi3518ev300.generic.config`）。
DUAL_ROLE 意味着**主机还是从机由设备树的 `dr_mode` 决定**，不是内核配置决定的。
若板子的 `dr_mode` 是 `peripheral`，插上 USB 网卡也不会枚举，`lsusb` 会是空的。

先在控制台确认：

```bash
lsusb                       # 空 = USB 侧没枚举
ls /sys/bus/usb/devices/    # 只有 usb1（root hub）也说明没有外设
```

这是**硬件/设备树层面**的问题，OpenIPC 的固件改不了 —— 需要确认板子 USB 口
是接成 host 模式（或 OTG 口有 ID 接地/正确配置）。上层 8188fu 等卡能用的板子，
同一路 USB 就能用本固件里的卡。

### 3.2 确认驱动真的注入了

```bash
iw dev                     # 应看到 wlan0，type monitor
ip -s link show wlan0      # TX packets 应持续增长
```

`TX packets` 不涨 = 注入没生效，八成是驱动绑错了或信道没切成功。

## 4. 改图传参数

### 4.1 链路参数（不重刷）

```bash
vi /etc/wfb.yaml
wifibroadcast stop
wifibroadcast start
```

**地面端必须完全一致**：`channel` / `width` / `mcs_index` / `fec_k` /
`fec_n` / `link_id`。差一个就收不到图。

#### `mlink` 与 MTU 的关系（这版有个自动兜底）

`mlink` 同时决定两件事：无线接口的 MTU，以及 majestic 的 NALU 上限
（`rtsp.naluSize = mlink - 100`）。本工程给的是 3994 —— 这和上游 OpenIPC
FPV 的**运行时**取值一致（上游打包的 `wfb.yaml` 写的是 1500，但它的
`video_settings` 里会 `cli -s .wireless.mlink 3994` 改掉）。

但 **Realtek USB 驱动不一定接受这么大的 MTU，而且 `ifconfig` 失败时未必
报错** —— 如果只下发不校验，就会出现「naluSize 按 3994 算、实际 MTU 还是
1500」的错配，majestic 产出的 NALU 被二次分片，反而更容易丢。

所以脚本设完 MTU 会回读 `/sys/class/net/wlan0/mtu`，按真实值反推 naluSize。
被驱动压下来时日志里会有一行：

```
驱动只接受 MTU 1500（请求 3994），按实际值调 naluSize
```

看到这行说明兜底生效了，功能正常，只是分片多一点。想知道实际生效值：

```bash
cat /sys/class/net/wlan0/mtu
cli -g .rtsp.naluSize
```

这两个数字应当满足 `naluSize == mtu - 100`。

#### `stbc` / `ldpc` 会按卡种自动调整

首次启动时脚本会按识别到的网卡改写 `/etc/wfb.yaml` 的这两项：

| 网卡 | stbc / ldpc | 原因 |
|---|---|---|
| RTL8812AU | **1 / 1** | 2x2，支持空时编码与 LDPC，远距更稳（与上游一致） |
| RTL8733BU | 0 / 0 | **1T1R，没有 STBC**，只能关（与上游一致） |

这两项**只影响发送端编码**，地面端 `wfb_rx` 会自动识别，不需要两边同步。
也就是说换卡不用动地面端。

写入会在日志里留痕，想确认现在的值：

```bash
wifibroadcast cli -g .broadcast.stbc
wifibroadcast cli -g .broadcast.ldpc
```

> 上游的做法是只写 yaml、不刷新本次运行的变量，所以那些值要等**第二次**
> 启动才生效。这版写完立即刷新，当次启动就生效。

### 4.2 视频参数

```bash
vi /etc/fpv-video.conf
rm -f /etc/system.ok        # 清除"已初始化"标记
killall -1 majestic
wifibroadcast start
```

或直接改运行时配置（立即生效，但不落到 fpv-video.conf）：

```bash
cli -s .video0.bitrate 6000
killall -1 majestic
```

改完想看当前值：

```bash
cli -g .video0.size
cli -g .video0.fps
cli -g .video0.codec
curl -s localhost/api/v1/config.json | jsonfilter -e "@.video0"
```

### 4.3 恢复出厂

```bash
wifibroadcast reset
```

## 5. 地面端怎么配

地面站（PixelPilot / aviateur / fpv4win / wfb-ng 手工）需要：

1. 把 `keys/gs.key` 放到地面端的 `/etc/gs.key`
2. 信道、带宽、MCS、FEC、`link_id` 与机上 `/etc/wfb.yaml` 一致
3. 频谱上确认没别人占 5805MHz

核对指纹（两边都要一致，否则只会看到雪花）：

```bash
sha256sum /etc/gs.key    # 应该能和 keys/PUBKEYS.txt 对上
```

## 6. 排障

| 现象 | 先查 | 常见原因 |
|---|---|---|
| 完全无图，地面端也收不到 wfb 包 | `iw dev`、`ip -s link` | 驱动没加载 / 注入失败 |
| 能收到包但全雪花 | 两边 `link_id`、`mcs_index`、`width` | 参数不一致 |
| 有图但花屏/卡顿 | `.video0.bitrate` 降到 6000 | 20MHz/MCS1 有效吞吐约 13Mbps，10Mbps 偏满 |
| 距离一远就断 | `txpower`、天线、`channel` | 换 149/153/157；确认 `iw reg set 00` 生效 |
| OSD 无数据 | `/etc/wfb.yaml` 的 `serial` | 改成 `ttyS1` 或 `ttyS0` |
| 颜色/曝光不对 | `SENSOR_INI` 与 IQ | 确认 `/etc/sensors/jxf23_i2c_1080p.ini` 与 `/etc/sensors/iq/f23.ini` 都在；IQ 缺失时会退到 `iq/default.ini`（imx307 的曲线），画面能出但颜色偏 |
| 启动就报 "未识别到受支持的 USB 无线网卡" | `lsusb` | VID:PID 不在表里，见 `/etc/fpv-usb-ids.txt` |

几个路径是**已核对过**的（对着上游 `hisilicon-osdrv-hi3516ev200.mk` 与
`wifibroadcast-ng.mk` 的安装规则查的，不是猜的）：

```
/etc/sensors/jxf23_i2c_1080p.ini   <- hisilicon-osdrv 的 files/sensor/config/*.ini
/etc/sensors/iq/f23.ini            <- 同上，files/sensor/iq/
/etc/sensors/high-fps/*.ini        <- 想上高帧率时换传感器用
/etc/drone.key                     <- wifibroadcast-ng 的 files/drone.key（本工程换成你的密钥）
/etc/wfb.yaml                      <- 同上
/etc/fpv-video.conf                <- 本工程加的，rootfs overlay
/usr/bin/wifibroadcast             <- 本工程替换的运行时脚本
/etc/init.d/S98wifibroadcast       <- 上游的，只调 wifibroadcast start/stop
```

深入排查时手动走一遍：

```bash
rmmod 8812au 8733bu 2>/dev/null
modprobe 8812au MaxTxBufLen=32
iw dev
iw wlan0 set monitor none
iw wlan0 set channel 161 HT20
iw dev wlan0 info
```

## 7. 安全提醒

### 7.1 先做这件事：设 root 密码

**这个镜像出厂时 root 没有密码，而且 SSH 是开着的。**

这不是我改出来的，是上游 OpenIPC 的默认行为，但你必须知道并处理：

| 事实 | 来源 |
|---|---|
| `BR2_TARGET_GENERIC_ROOT_PASSWD=""` —— root 空密码 | Buildroot 配置（最终 `.config` 第 478 行） |
| `BR2_PACKAGE_DROPBEAR_OPENIPC=y` —— SSH 服务在跑 | defconfig |
| dropbear 启动参数 `-R -B -k -p 22 -K 300` | 上游 `/etc/init.d/S50dropbear`，其中 **`-B` 就是「允许空密码登录」** |
| `CONFIG_HISI_FEMAC=y` —— 板子有以太网 MAC | 内核配置 |

也就是说：**只要有网络通路，任何人都能免密 ssh 进去**。串口控制台同理。

刷完机第一件事，接串口或用网线登录后立刻执行：

```sh
passwd root
```

更彻底一点，关掉空密码登录并改用密钥：

```sh
# 1) 把公钥放进 /etc/dropbear/authorized_keys
mkdir -p /etc/dropbear
cat > /etc/dropbear/authorized_keys <<'EOF'
ssh-ed25519 AAAA...你的公钥...
EOF
chmod 700 /etc/dropbear
chmod 600 /etc/dropbear/authorized_keys

# 2) 去掉启动参数里的 -B（空密码放行），并锁定密码登录
sed -i 's/DAEMON_ARGS="-R -B -k -p 22 -K 300"/DAEMON_ARGS="-R -k -s -p 22 -K 300"/' \
    /etc/init.d/S50dropbear
/etc/init.d/S50dropbear stop
/etc/init.d/S50dropbear start
```

`-s` 表示禁止密码登录、只接受公钥。改完**先在另一个会话里验证能进**，再退出当前会话。

> 想一劳永逸，也可以在 `defconfig` 里写死密码哈希（不推荐，因为会进 git）：
> ```
> BR2_TARGET_GENERIC_ROOT_PASSWD="$(echo -n '你的密码' | mkpasswd -m sha-256 -s)"
> ```

### 7.2 密钥

- `drone.key` 与 `gs.key` 是一对。**只泄露一个**时别人解不了你的图，
  但能重放/干扰；两个都泄露就是完全公开。
- 不要把 `gs.key` 提交进 git、不要发群里、不要贴聊天框。
- 换密钥：`keys/gen-keys.py` 重新生成 → 重刷机上镜像 → 地面端换 `gs.key`。

**注意 `.bin` 本身也带着密钥。** 镜像里的 `/etc/drone.key` 就是你那份
`keys/drone.key`，而那个文件的前 32 字节是机载端私钥、后 32 字节是地面端
公钥 —— 会话密钥正是由这两者算出来的。所以：

- **别把编好的 `.bin` 发到公开的地方**（论坛、网盘、群文件都不行）。
- 想分享固件给别人测试，先用 `keys/gen-keys.py` 重新生成一套再构建，
  这样分享出去的那份固件对应的密钥与你自己的无关。
- 只有 `keys/PUBKEYS.txt`（公钥 + 指纹）是可以安全分享的，用它核对两边
  是不是同一对即可。

### 7.3 其它

- `wlan0` 被 wifibroadcast 放进 monitor 模式，它不承载 IP —— 地面端的
  `wfb_rx` 收到的是原始注入帧，不会给你一个能 ssh 的 IP 网段。所以真正的
  暴露面是**串口**和**以太网口**（若你配了 `eth0`）。
- 这台设备发的是你自己的视频信号。`link_id` 只是把不相干的流量过滤掉，
  **不是**认证手段 —— 真正的机密性来自 X25519 那一对密钥。
