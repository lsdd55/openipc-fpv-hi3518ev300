## 1. USB Wi-Fi 驱动矩阵

目标内核：**Linux 4.9.37**（海思 SDK 锁定，由 `openipc/linux` 提供）。

| 芯片 | 模块名 | 来源 | 4.9 可行性 | 依据 |
|---|---|---|---|---|
| RTL8812AU / RTL8811AU | `8812au.ko` | `openipc/realtek-wlan` 分支 `rtl8812au_fpv` | ✅ 上游在用 | `general/package/rtl8812au-openipc/rtl8812au-openipc.mk` |
| RTL8733BU | `8733bu.ko` | `openipc/realtek-wlan` 分支 `rtl8733bu_fpv` | ✅ 上游在用 | 同上，且 `.mk` 里用 `findstring fpv` 选 FPV 分支 |
| RTL8814AU | — | 仅 `aircrack-ng/rtl8814au` | ❌ **不编入** | 见 §1.2 |
| RTL8812CU / RTL8822CU | — | 仅 `libc0607/rtl88x2cu` | ❌ **不编入** | 见 §1.3 |
| MT7921AU | — | 仅 `mt76/mt7921u` | ❌ 不可行 | 见 §1.4 |

`realtek-wlan` 仓库实际只有这些分支（`git ls-remote` 实测）：

```
rtl8188fu  rtl8189fs  rtl8733bu_fpv  rtl8733bu  rtl8811cu  rtl8812au_fpv  rtl8812au
```

两个驱动都在上面这张表里，本工程直接用上游的包，**不需要自己封包**。

### 1.1 上游 .mk 里为什么同时给 `CONFIG_X=y` 和 `CONFIG_XU=m`

本工程不含自建驱动包，这一节保留是因为排障时会在上游 `.mk` 里看到这种写法。

Realtek 的 out-of-tree Makefile 用两个用途不同的符号：

- `CONFIG_RTL88XXA=y` 这类开关决定**选哪个 HAL** —— 它决定 `MODULE_NAME` 的取值
- `obj-$(CONFIG_RTL88XXAU) := $(MODULE_NAME).o` 决定这个 `.o` **出不出**

只给 `=m` → 第一个开关不成立，`MODULE_NAME` 为空，产物名字是错的；
只给 `=y` → `obj-$(...)` 展开成 `obj-y`，模块被编进内核而不是独立的 `.ko`。

上游 `rtl88x2eu-openipc.mk` 只给了一个 `CONFIG_RTL8822EU=m`，是因为那是另一份
打过补丁的代码库（`libc0607/rtl88x2eu-20230815`），**不能照抄到别的驱动上**。

### 1.2 RTL8814AU：评估后不编入

曾评估过 `aircrack-ng/rtl8814au`（分支 `v5.8.5.1` @ `8926414`）。它是 4x4 卡，
4.9 支持有硬证据 —— 其 CI 矩阵明确编译 `KVER=4.9.219`，技术上可用。

**不编入的原因是体积**：模块在镜像里约占 0.5–0.6 MB，而 16 MB flash 的余量本来
就不宽；8812AU 能覆盖同样的使用场景。移除后本工程**没有任何自建驱动包**，两个驱动
都走上游现成的 `rtl8812au-openipc` / `rtl8733bu-openipc`。

顺带记一条选源教训：`morrownr/8814au` 的 README 明写支持 **5.4–6.18.x**，
在 4.9.37 上编不过 —— 选源前必须先看这个 badge，别凭「代码看着老」下判断。

### 1.3 RTL8812CU：评估过，最终不编入

RTL8812CU 与 RTL8822CU 同属 Realtek **8822C** 硅片族，唯一可用的驱动是
`libc0607/rtl88x2cu`（设备 ID 实测：`0bda:c812 0bda:c82c 0bda:c82e
0bda:d820 0bda:d82b 13b1:0043`）。

**为什么最后砍掉：**

- 作者 README 只写「Build on kernel 6.12」，**没有 4.9 实证**
- `osdep_service_linux.h` 的 `LINUX_VERSION_CODE` 守卫虽然下探到 2.6/3.x，
  但那只是「代码里还留着旧分支」，不等于在 4.9.37 上编过
- 剩下两张（8812AU / 8733BU）都有 4.9 依据，覆盖的能力范围已经够用，
  没有为第三张冒构建失败的必要
- 省下约 0.6 MB 的 flash —— 16 MB 的余量本来就不宽

`rtl8812au-openipc`、`rtl8733bu-openipc` 两个包保留（都是上游现成的）。
若哪天确实需要 8822C 系，把 `libc0607/rtl88x2cu` 重新封包即可，注意它的模块名
是条件赋值（`CONFIG_BT_COEXIST=n` → `8812cu.ko`，`=y` → `88x2cu.ko`）。

### 1.4 MT7921AU 为什么不可行

唯一驱动是 mt76 的 `mt7921u`。现存独立发布版 `morrownr/mt76` 自述：

> Supports DKMS, non-DKMS, Secure Boot, and **kernels 6.12 through 7.4**.
> Kernels older than 7.0 are best effort.

内核 4.9.37 与 6.12 之间隔了 cfg80211/mac80211 的多轮 ABI 重构
（`ieee80211_ops` 增删成员、`cfg80211_ops` 增删成员、`struct station_info`
扩容、`WARN_ON` 语义变化等）。往 4.9 回移 mt76 等价于把 5.x 的整个无线
子系统搬过来 —— 不是打补丁，是重写，且没有上游维护路径。

**可行的替代：**

1. **换网卡**：RTL8733BU（体积小、功耗低）或 RTL8812AU（生态最成熟）
2. **换 SoC 平台**：需要 MT7921AU 就走内核 5.10+ 的
   SigmaStar SSC338Q / Goke GK7205V300 等，OpenIPC 在这些平台上有 5.x 内核
3. **等**：若海思侧将来放出 5.x BSP（目前没有迹象）

### 1.5 RTL8812AU 也要留意：上游海思 defconfig 里没人用它

实测海思各 defconfig 启用的无线包：

```
hi3518ev300_ultimate_defconfig    BR2_PACKAGE_RTL8188FU_OPENIPC  BR2_PACKAGE_RTL8189FS_OPENIPC
hi3518ev300_lite_defconfig        <无>
hi3516ev200_ultimate_defconfig    <无>
hi3516ev300_ultimate_defconfig    BR2_PACKAGE_RTL8188FU_OPENIPC
```

也就是说 **`rtl8812au-openipc` 在海思 4.9 上没有被上游 defconfig 直接验证过**。
它确实被启用（走 `rtl8812au_fpv` 分支），但那是通过 CI 的
「base defconfig + fragment」路径给 FPV 变体加的，我没能拿到确切的
内核版本组合证据。

同理 `ssc338q_ultimate_defconfig` 启用了 `BR2_PACKAGE_RTL8733BU_OPENIPC`，
说明 **RTL8733BU 在 4.9 上有上游实证** —— 三张卡里它是最稳的。

排序结论：

| 驱动 | 4.9 把握 | 依据 |
|---|---|---|
| RTL8733BU | **高** | 上游 `ssc338q_ultimate_defconfig` 在 4.9 上直接启用 |
| RTL8812AU | 中 | 上游有用（`rtl8812au_fpv` 分支），但无海思 defconfig 直接证据 |

两张卡里，**RTL8733BU** 有上游 defconfig 的直接证据（`ssc338q_ultimate_defconfig`
在 4.9 上启用它）；**RTL8812AU** 上游在用 FPV 分支，但没有海思 defconfig 的
直接证据，所以给「中」。

RTL8812CU 与 RTL8814AU 都已按这个判断移除：前者没有 4.9 依据，后者体积不划算。
两次移除合计省下约 1.1 MB flash。

### 1.6 `8812au` 还是 `88XXau`？—— 两个分支各叫一个名

同一个驱动的两个 fork 用的模块名不同，写错了 `modprobe` 会直接找不到模块：

| 来源 | `MODULE_NAME` |
|---|---|
| `openipc/realtek-wlan` @ `rtl8812au_fpv`（**本工程用的**） | `8812au` |
| `aircrack-ng/rtl8812au` | `88XXau` |

证据：OpenIPC 分支 `Makefile` 的 `HAL_RTL8812A_RTL8821A` 段是无条件赋值

```make
ifneq ($(CONFIG_RTL8812A)_$(CONFIG_RTL8821A), n_n)
RTL871X = rtl8812a
ifeq ($(CONFIG_USB_HCI), y)
MODULE_NAME = 8812au
endif
```

`/usr/bin/wifibroadcast` 按 `8812au` 加载，并把 `88XXau` 留作回退名与卸载用 ——
这样即使镜像里混进过另一个分支编出来的模块，也不会卡住。

## 2. USB 主机控制器

`hi3518ev300.generic.config` 实测：

```
CONFIG_USB=y
CONFIG_USB_DWC3=y
CONFIG_USB_DWC3_DUAL_ROLE=y
CONFIG_USB_DWC3_OF_SIMPLE=y
CONFIG_USB_XHCI_HCD=y
CONFIG_PHY_HISI_XVP_USB2=y
CONFIG_USB_EHCI_HCD is not set
CONFIG_USB_OHCI_HCD is not set
```

即 DWC3 控制器 + 海思 USB2 PHY，双角色。做 host 没问题。

**结论：不需要改内核配置。** 这也是上游同一份 config 能跑
`rtl8812au` / `rtl8733bu` 的原因。

容量提示：单口 USB 2.0，理论 480 Mbps，实测 wfb 注入可用约 20~25 Mbps。
多卡并发需外供电 HUB，且共享同一控制器带宽。

## 4. 传感器 F23

### 4.1 上游已有的资产

```
general/package/hisilicon-osdrv-hi3516ev200/files/sensor/
├── config/jxf23_i2c_1080p.ini      # 传感器模式（注意前缀是 jxf23，不是 f23）
├── iq/f23.ini                      # IQ 调校
└── libsns_f23.so                   # 传感器驱动（34984 字节）
```

`hisilicon-osdrv-hi3516ev200.mk` 会把 `config/*.ini`、`iq/f23.ini`、
`*.so` 全部装到设备的 `/etc/sensors` 与 `/usr/lib/sensors` —— F23 开箱可用。

### 4.2 为什么只能 1080p30

`libsns_f23.so` 的字符串常量里只有两个模式入口：

```
soi_sensor_linear_1080p30_init
soi_sensor_2wdr1_1080p30_init
```

并带拒绝路径：

```
Not support Fps: %f
Not support! Width:%d, Height:%d, Fps:%f, WDRMode:%d
```

`jxf23_i2c_1080p.ini` 同样是单一模式：

```ini
[isp_image]
Isp_FrameRate=25
Timingblank_VsyncVact=1080
DevRect_w=1920
DevRect_h=1080
```

**没有 720p 模式，也没有 60fps 模式。** 720p60 无法实现。

### 4.3 需要 60fps 时的换装方案

同一颗 Hi3518EV300、同一份固件，上游已备好 60fps 档位（
`files/sensor/config/high-fps/`）：

| 传感器 | 文件 | 分辨率/帧率 |
|---|---|---|
| IMX307 | `imx307_1280x720_60fps.ini` | 720p60 |
| IMX307 | `imx307_1920x1080_60fps.ini` | 1080p60 |
| IMX307 | `imx307_368x304_200fps.ini` | 368x304@200 |
| IMX307 | `imx307_640x480_130fps.ini` | 640x480@130 |
| IMX335 | `imx335_1920x1080_55fps.ini` | 1080p55 |
| IMX335 | `imx335_1296x972_64fps.ini` | 1296x972@64 |
| IMX335 | `imx335_1280x720_120fps.ini` | 720p120 |
| IMX335 | `imx335_800x480_240fps.ini` | 800x480@240 |

换装后改 `/etc/fpv-video.conf` 的 `SENSOR_INI`，并把 `VIDEO_FPS`/`VIDEO_SIZE`
调到对应值。

### 4.4 编码器上限

Hi3518EV300 VENC 上限约 62 Mpixel/s（1080p30）：

| 目标 | 像素率 | 结论 |
|---|---|---|
| 1920x1080@30 | 62.2 M/s | 上限，可行 |
| 1280x720@60 | 55.3 M/s | 编码器可行，**传感器不可行** |
| 1920x1080@60 | 124.4 M/s | 编码器与传感器都不可行 |

即：720p60 的瓶颈确实在传感器而非编码器，换 IMX307 即可解锁。

## 5. 构建环境：为什么镜像必须在 CI 出

本工程开发环境（Windows + WSL2）**无法完成本地全量构建**。不是配置问题，
是网络条件限制。以下全是实测数据，不是猜测。

### 5.1 网络实测

| 探测项 | 结果 |
|---|---|
| 出口代理 | `http://127.0.0.1:7890`（绕过代理直连 = HTTP 000，完全不通） |
| `raw.githubusercontent.com` 小文件 | ✅ 稳定（本文档所有驱动证据都由它取得） |
| `mirrors.tuna.tsinghua.edu.cn` 单个 .deb | ✅ 稳定（`cpio` 就是这么装上的） |
| `archive.ubuntu.com:80`（apt 默认） | ❌ 连接超时 |
| `archive.ubuntu.com:443` | ❌ SSL connection reset by peer |
| `codeload.github.com` 源码 tarball（76.5 MB） | ❌ 20,766,739 B 处断流，8 次续传零进展 |
| `ghproxy.net` / `ghfast.top` / `gh-proxy.com` / `github.moeyy.xyz` | ❌ 15.7 MB / 1.3 MB / 1.5 MB / 0 B |
| HTTP Range 分块下载 | ❌ 服务端忽略 `Range`，永远回 `200` + 完整包 |
| 强制 `--http1.1` + `Range` | ❌ 仍是 `200` 而不是 `206` |

规律：**单次传输在约 15–20 MB 处被切断，且无法续传。**

### 5.2 构建需要下载什么

| 依赖 | 体积 | 能否获得 |
|---|---|---|
| Buildroot 2024.02.10 | ~10 MB | ✅ 本地已成功下载 |
| 预编译工具链 `toolchain.hisilicon-hi3516ev200.tgz` | **98.5 MB**（`103298264` 字节） | ❌ 远超切断阈值 |
| 内核源码 `openipc/linux` 的 `hisilicon-hi3516ev200` 分支 | 上百 MB | ❌ 同上 |
| 各包源码 | 零散，多数 < 20 MB | 部分可行 |

工具链这一项单独就决定了本地构建不可行。

（顺带记下正确地址，`general/external.mk` 里定义：
`OPENIPC_KERNEL := hisilicon-hi3516ev200`，
`OPENIPC_TOOLCHAIN := toolchain/toolchain.hisilicon-hi3516ev200`，
所以 release 资产路径带一层 `toolchain/` 前缀。）

### 5.3 但配置层是真的验证过了

大文件拿不到，不代表什么都验证不了 —— **kconfig 只需要小文件**。
实际做法：用 GitHub API 取到全量 blob 清单，逐文件下载重建了够跑 kconfig 的
最小树（173 个文件，8 并发，全部成功），然后真跑：

```
make BOARD=hi3518ev300_fpv_wfbng defconfig      ->  rc=0
configuration written to .../output/.config
```

产物核对（真实 Buildroot 2024.02.10 + 上游 `9f0639e` 的 Kconfig）：

```
BR2_OPENIPC_SOC_MODEL="hi3518ev300"     BR2_OPENIPC_SOC_FAMILY="hi3516ev200"
BR2_OPENIPC_VARIANT="fpv"               BR2_OPENIPC_FLASH_SIZE="16"
BR2_OPENIPC_SNS_MODEL="f23"             BR2_PACKAGE_MAJESTIC=y
BR2_PACKAGE_WIFIBROADCAST_NG=y          BR2_PACKAGE_YAML_CLI_MULTI=y
BR2_PACKAGE_RTL8812AU_OPENIPC=y
BR2_PACKAGE_RTL8733BU_OPENIPC=y
```

并且与上游 `hi3518ev300_ultimate_defconfig` 做了差分：

- 新增项恰好是预期那批：`WIFIBROADCAST_NG`、`IW`、`MAVFWD`、`MSPOSD`、
  `JSONFILTER`、`LIBUBOX`、四个 RTL 驱动、`SNS_MODEL=f23`、`VARIANT=fpv`
- 删除项恰好是主动裁掉那批：mosquitto / wireguard / zerotier / uacme / vtund /
  lame / quirc / divinus / 8188fu / 8189fs，及其传递依赖
  mbedtls / libjpeg / miniupnpc / natpmp

> **一处需要更正的说法**：早先我把 `opus` / `libogg` 也列进了「已裁掉」，
> 那是错的。`majestic.mk` 里声明了
>
> ```
> MAJESTIC_DEPENDENCIES = ... libogg-openipc opus-openipc
> ```
>
> Buildroot 按 `.mk` 的依赖图建包，**kconfig 里的 `# BR2_PACKAGE_OPUS_OPENIPC
> is not set` 拦不住它**。`br-show-info` 可以印证：`opus-openipc`（1.3.1）与
> `libogg-openipc`（1.3.5）都在依赖图里，`reverse_dependencies = ["majestic"]`。
> 两者合计约 400 KB，是去不掉的开销 —— 除非不做音频，而 majestic 不支持
> 编出无音频变体。见 §6 的 flash 预算。
- kconfig **零「未定义符号」告警**

也就是说：defconfig 的每个符号都在真实 Kconfig 里存在且被正确接受，
`wifibroadcast-ng` 的 `select` 依赖（iw / mavfwd / msposd / jsonfilter /
yaml-cli / yaml-cli-multi / curl / libevent）全部落地。

在此基础上又把上游 164 个 `package/**/*.mk` 取齐，让 Buildroot 做**完整包解析**：

```
make BOARD=hi3518ev300_fpv_wfbng br-show-info     ->  rc=0，86 个包
```

两个新包被正确登记，版本等于固定的提交，依赖链是
`linux, toolchain, skeleton, host-ccache, host-skeleton, host-tar`
—— 正是 `kernel-module` 包应有的形状。归档下载地址也验过（200 + gzip）。
细节见 `README.md` §7.3。

### 5.4 顺带发现并修复的**上游缺陷**

`yaml-cli-multi` 这个包在上游是坏的：

```
general/package/yaml-cli-multi/Config.in         存在，定义 BR2_PACKAGE_YAML_CLI_MULTI
general/package/wifibroadcast-ng/Config.in:24    select BR2_PACKAGE_YAML_CLI_MULTI
general/package/adaptive-link/Config.in:6        select BR2_PACKAGE_YAML_CLI_MULTI
general/package/Config.in                        只有 yaml-cli，没有 yaml-cli-multi 的 source 行
```

上游 165 行的 `Config.in` 里 `yaml-cli-multi` 出现 **0 次**（已用原始文件核对）。
后果：该符号永远不进 `.config`，`yaml-cli-multi` 二进制不会被编进任何镜像 ——
而 `wifibroadcast-ng` 的运行脚本要用它把 `wlan_adapter` 写进 `/etc/wfb.yaml`。
kconfig 不会对此报警，所以这是个**静默失败**。

本项目在 overlay 里补上了这一行 `source`
（`scripts/patch-config-in.py` 的第三条规则），并已实测
`BR2_PACKAGE_YAML_CLI_MULTI=y`。

### 5.4.1 修好上面那处之后，又暴露出第二个缺陷

第一个缺陷（没人 `source`）意味着这个包**从来没被构建过**，所以它里面的
另一处错误也一直没人碰到。一旦它会真的构建，问题立刻出现：

```make
YAML_CLI_MULTI_VERSION = 'a633865b5202dcd1f4f548e8486d3a334c79c03c'
                        ^                                    ^
                        字面单引号
```

make **不剥**单引号，这个值原样进入 `$(call github,…)` 拼出的下载地址：

```
https://github.com/vertexodessa/yaml-cli-multi/archive/'a633865…'   -> HTTP 404
https://github.com/vertexodessa/yaml-cli-multi/archive/a633865…     -> HTTP 200 + gzip
```

两个地址都实测过。也就是说：修好 `source` 却不修这里，构建会**在下载阶段
404 失败**。

本工程在 overlay 里放了一份修正的
`general/package/yaml-cli-multi/yaml-cli-multi.mk`（只去掉那两个引号，
其余与上游一致）。用真实 Buildroot 解析后确认版本字段已干净：

```
yaml-cli-multi: version=a633865b5202dcd1f4f548e8486d3a334c79c03c
    https://github.com/vertexodessa/yaml-cli-multi/archive/a633865b…
```

> 这两个缺陷是叠加的 —— 第一个把第二个藏起来了。`tests/validate-config.py`
> 现在对两者都有断言，任何一个被改回去都会立刻报错。

### 5.5 结论

镜像必须在 CI 出 —— 你原本选的也是 GitHub Actions，那边网络正常，不受影响。
本地能做的是静态校验与真实 kconfig 验证，都已经做完。

若将来要在本地编：把上面几个域名放通，或预先准备 `BR2_DL_DIR` 缓存
（含工具链与内核源码），再跑 `scripts/build.sh`。

## 6. 16MB flash 的预算与上限

最终产物是一个 `firmware.bin` =「uImage + squashfs 背靠背」，由
`general/scripts/post-image-split.sh` 生成，写到 flash 的 `0x50000` 处，
内核启动时自己把它切成 kernel / rootfs / rootfs_data。所以真正要装下的
只是这一个文件。

上限有两个，**任一超出上游 `make` 都会直接失败**：

| 检查项 | 上限 | 出处 |
|---|---|---|
| `firmware.bin` 总大小 | **15808 KiB** = 16×1024 − 320（`0x50000` 偏移）− 256（尾部保留） | `Makefile` 的 `CHECK_SIZE` |
| `uImage` | **2048 KiB**（2 MiB） | `CHECK_KERNEL_READ`，bootloader 只读这么多 |

`uImage` 这一项与你没改过的上游完全一致（同一份内核配置），所以变量只有
squashfs —— 四个 WiFi 驱动模块都装在 rootfs 里。

### 6.1 三个驱动大概吃多少

驱动以 `.ko` 装进 `/lib/modules/4.9.37/`，经 `--strip-unneeded`
（`general/external.mk` 里 `LINUX_MAKE_FLAGS += INSTALL_MOD_STRIP=--strip-unneeded`），
再被 squashfs 的 XZ 压一遍：

| 模块 | 裸 `.ko` 量级 | 镜像里量级 |
|---|---|---|
| `8812au.ko` | 1.5–2 MB | 0.6–0.8 MB |
| `8733bu.ko` | 0.6–0.8 MB | ~0.3 MB |
| 合计 | | **约 0.9–1.2 MB** |

典型 hi3516ev200 的 uImage 约 2.4 MB，ultimate 级 rootfs 约 6–8 MB，
加上这些模块总量大致 **10–12 MB**，落在 15808 KiB 内但余量不宽。

> ⚠️ 以上是**量级估算，不是实测**。以构建时 `CHECK_SIZE` 打印的
> `- firmware.bin: [NKB/15808KB]` 为准；剩余不足 32 KiB 时上游会打
> headroom warning，CI 的「体积报告」步骤也会把这些数字写进 job summary。

#### 去不掉的其他开销

有几样东西看着可以裁，实际裁不掉，估算余量时要算进去：

| 项 | 量级 | 为什么去不掉 |
|---|---|---|
| `opus-openipc` + `libogg-openipc` | 约 400 KB | `majestic.mk` 里 `MAJESTIC_DEPENDENCIES` 直接声明，kconfig 符号拦不住（详见 §5.4 的更正） |
| `majestic` 本体 | 数 MB | 整个 FPV 图传的 H.264 编码就靠它 |
| `majestic-webui` | 1–2 MB | 网页配置界面。**这是真正能裁的一项**，见 §6.2 |

也就是说：真到了要抠空间的时候，`majestic-webui` 和多余的传感器库是
第一顺位，`opus`/`libogg` 不是 —— 把它们从 defconfig 里注释掉不会产生
任何效果。

### 6.2 真的超了怎么办

按「最不常用」顺序裁，每裁一项都是改 defconfig 重新构建：

1. `BR2_PACKAGE_MAJESTIC_WEBUI` —— 网页配置界面；SSH 仍然可用
2. `BR2_PACKAGE_RTL8733BU_OPENIPC` —— 8812AU 已覆盖主流程
3. `BR2_TARGET_ROOTFS_UBI` / `UBIFS` 相关 —— 本板是 NOR，NAND 镜像用不到
   （不影响 `firmware.bin` 大小，但能省构建时间）

### 6.3 顺带记下产物名

`REPACK_NOR_SPLIT` 产出：

```
output/images/firmware.bin                      原始固件
output/images/firmware.bin.hi3518ev300           同名副本
output/images/openipc.hi3518ev300-nor-fpv-split.tgz   tar 包（含 .md5sum）
```

`openipc.hi3518ev300-nor-<VARIANT>-split.tgz` 里的 `<VARIANT>` 就是
`BR2_OPENIPC_VARIANT` 的**原值直接拼进去** —— 所以它绝不能含斜杠，
否则 `tar -czf` 会把它当子目录而在**构建最后一步**失败。这也正是本工程把
VARIANT 从 `fpv/wfbng` 改成 `fpv` 的原因：同样的斜杠还会让
`$(filter fpv wfbng,$(VARIANT))` 匹配不到，悄悄丢掉 IMX307/IMX335 的
高帧率传感器库（`hisilicon-opensdk.mk:344`）。

实测（纯 make 验证）：

```
VARIANT=fpv        findstring=[fpv]  filter=[fpv]     <- 命中
VARIANT=fpv/wfbng  findstring=[fpv]  filter=[]        <- filter 不命中
```
